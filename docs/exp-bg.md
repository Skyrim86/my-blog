# 动态背景（WebGL shader）能不能上 —— 实测报告

- 日期：2026-09-21/22 夜
- 机器：Windows 11 / RTX 5060 Laptop GPU（ANGLE D3D11）/ 屏幕 1280×800 逻辑 = 2560×1600 物理 @ dpr 2
- 被测站点：`my-blog` 只读参考的 `public/`（`serve_public.py 8794`，未改主仓库、未改 `lab/`）
- 结论一句话：**能上**。原型在出货分辨率下的 GPU 代价是 **0.13 ms/帧（6.06 ms 帧预算的 2.1%）**，
  主线程 0.007 ms/帧；真实页面帧间隔 A/B 里**量不到可归因于它的掉帧**。但必须带降级/暂停策略，
  且真正要盯的是 **canvas 像素数**，不是 shader 复杂度。

---

## 0. 先修正两个前提（量出来的，不是猜的）

| 前提 | 实测 | 影响 |
|---|---|---|
| 帧预算 | rAF 间隔 p50 **6.1 ms**、p10 6.0 ms → **166.7 Hz**（`diag.py`） | 与任务给的 6.06 ms 一致 |
| 视口大小 | `frameab.py` 的 1200×760 窗口在 dpr=2 下实测 **2338×1340 = 3.13 Mpx**（CSS 1169×670） | 屏幕 2560×1600 = 4.1 Mpx 的 **76%**，所以「小窗口量不出全屏问题」这个担心不成立，本组数字对全屏是有代表性的 |
| GPU | `ANGLE (NVIDIA, NVIDIA GeForce RTX 5060 Laptop GPU …, D3D11)` | 独显。弱核显的代价**未测**，见 §8 |
| GPU 计时 | `EXT_disjoint_timer_query_webgl2` **可用**（`EXT_disjoint_timer_query` 不可用） | 于是不用只靠外推，可以**直接量 shader 占了多少 GPU 时间** |

## 1. 原型

`bg-shader.js`（单文件，145 行，含注释 ~10 KB）：
全屏 `<canvas>`（`position:fixed; inset:0; z-index:-1; pointer-events:none`）+ 一个缓慢流动的极光
fragment shader（3 层 fbm 值噪声 + 3 条正弦带 + 静态星野）。无交互、无外部资源。

**挂载点是 `<html>` 的第一个子节点**（不是 body）：`body::before`（壁纸图 + 文字对比蒙版）与
`body::after`（玻璃质感层）同为负 z-index，在根层叠上下文里按树序绘制，canvas 排在 `<body>` 之前
→ 绘制顺序 = `<html>` 底色 → canvas → `::before` 蒙版 → `::after` 质感 → 正文。
实测确认（`probe.py`）：`bgIdx=0, bodyIdx=2, beforeZ=-1`，即 canvas 垫在蒙版与质感层之下。

**替换而不是叠加**：`nobg.js` 把 `--bg-image-light/dark` 设为 `none`（inline custom property 胜过
模板生成的 `:root[data-bg=...]`），蒙版 `--bg-mask-*` 不动 —— 实测 `body::before` 的 backgroundImage
变成 `linear-gradient(...), none`，即「图没了、蒙版还在」，对比度模型照旧。

截图核对（`probe-final-1.png`）：页面背景是深色极光 + 星野，没有残留照片壁纸，正文/卡片/导航都在它之上，
可读性正常。静态臂 `probe-base-static-1.png` 是原插图壁纸。

**踩到的坑（第一版就是这么死的，写进代码注释了）**：`Page.addScriptToEvaluateOnNewDocument` 注入
的脚本跑在「document 还是空的」那一刻，`document.documentElement === null`；直接
`insertBefore` 抛 TypeError，整支脚本静默死掉（探针里表现为 `window.__bg === undefined`）。
必须等 `documentElement` 出现（MutationObserver）再初始化。

## 2. 仪器改造（`lab/shots/frameab.py` → `frameab2.py`）

原版只支持注入 CSS。本实验要注入 JS 脚本、开弹层、交错轮次、保留原始数据，所以复制改造
（`lab/` 只读未动）：

1. `variants` 支持 `js`（`Page.addScriptToEvaluateOnNewDocument`，shader 因此和真上线一样首屏就在）、
   `setup`（导航后、录制前执行，如 `window.homeDeck.openAt(0)`）、`drag`（录制中每帧在 3D 卡 canvas 上
   派发合成 pointermove，把卡「拖着不放」，让它的 rAF 不停 —— 卡的 `frame()` 里有「静止就停」，
   不拖的话它 1.4 s 后就自己停了，那是另一种状态)。
2. **轮次交错**：外层轮次、内层臂，这样同一轮的臂共享环境条件；并支持把逐轮原始帧间隔落盘。
3. 每臂前后 `Page.bringToFront`，且**录制前断言 `document.visibilityState === 'visible'`**。
4. `--extra-flags`（跑 `--disable-gpu` 代理）、`--out`（原始 JSON）。

**这场实验里被测量工具本身坑到的三件事，都必须记住：**

- **站点 CSS 的 `scroll-behavior: smooth`**：`window.scrollTo(0,0)` 会启动一段动画，而录制是在
  「动画还在跑」之后立刻开始的 → 第一版所有臂 300 帧只滚了 **23.5 px**（几乎等于没滚），
  测出来的 p99 全是 6.2 ms 的「很流畅」。修法：**先把 `documentElement.style.scrollBehavior`
  设 `auto`，再 `scrollTo(0,0)`**。
- **窗口被别的窗口盖住 → `visibilityState=hidden` → rAF 不跑 → `__f` 数组是空的**。
  第一版有一次整轮 0 帧，差点被读成「流畅」。修法：加 3 个 Chromium 开关
  （`--disable-backgrounding-occluded-windows`、`--disable-renderer-backgrounding`、
  `--disable-background-timer-throttling`，与原有的 `--disable-features=CalculateNativeWinOcclusion`
  并用）+ 录制前 visibility 断言 + `frames<30` 的轮次自动重测并标 `bad`。
- **首轮必丢**：首页第一轮几乎每次都是坏的（与其他实验的负载无关也如此）—— 原始数据里
  `4x` 臂的**第 1 轮永远干净、第 2/3 轮才崩**，就是这一条的另一面。分析时以轮为单位看，并单独给第 1 轮。

另外两个刻意的选择：
- **滚动改为 ping-pong**：原版 200 帧 × 250 px 单向滚，长页面滚到底之后剩下的帧没有滚动负载。
  改成撞边界就反向，保证全录制期都有滚动负载。
- **步长按页长自适应**：`step = min(250, max(2, round(maxY/25)))`。首页 `scrollH=943`（maxY 273 px）
  用 250 px 一步会退化成「上下两点来回」，所以首页实际是 11 px/帧（1815 px/s，接近真人）；
  重页 `/courses/regression-analysis/chapter-01/notes/`（`scrollH=16233`，maxY 15563）是 250 px/帧
  （41250 px/s，**故意的极端值**）。两个页面的负载性质不同，见 §4.3。

## 3. 直接量到的代价（本次实验最硬的一组数字）

`gputime.py`：用 `EXT_disjoint_timer_query_webgl2` 在**真窗口**里逐帧包住 `drawArrays`，读最近 60 帧分布。

| 分辨率倍率 | canvas 像素 | GPU p50 | p90 | max | 占 6.06 ms 预算 |
|---|---|---|---|---|---|
| 1.0（出货配置） | 3.13 Mpx | **0.129 ms** | 0.132 | 0.135 | **2.1%** |
| 1.0，噪声降到 1 层 | 3.13 Mpx | 0.077 ms | 0.085 | 0.090 | 1.3% |
| 2.0 | 12.53 Mpx | 0.519 ms | 0.526 | 0.530 | 8.6% |
| 4.0 | 50.13 Mpx | 1.368 ms | 1.740 | 1.754 | 22.6% |
| 4.0 + 20 层噪声（压力对照） | 50.13 Mpx | **8.090 ms** | 10.307 | 11.905 | **133%** |

主线程侧（`drawArrays` 提交耗时累计）：**5–11 µs/帧**（0.1–0.2%），且随分辨率几乎不变 →
**代价全在 GPU 上，主线程没被占**。

**仪器可信度自证**（不是自说自话）：
1. 代价随像素几乎线性（0.077 → 0.129 → 0.519 → 1.368 ms），随噪声层数单调增大（1 层 vs 3 层：
   0.077 vs 0.129）；
2. 最后那一行是**预测性验证**：4x + 20 层量到 8.09 ms > 6.06 ms 帧预算，同一轮里 rAF 实测帧数掉到
   **188/2.2 s ≈ 85 fps** —— 计时器说超预算，帧率就真的掉了。所以这组数不是噪声。

> 口径提醒：计时器只包住 **shader pass**，不含「把这个 canvas 合成进页面」的代价。§4.4 会看到
> 这一项在小画布上无所谓，在大画布上是压垮帧预算的真正原因。

## 4. 真实页面的帧间隔 A/B

原始数组全部落盘（每个文件里每臂每轮都有完整 `gaps` 数组）。下面每张表的「>7ms / >12ms」是
**每轮 299 帧里超过一帧预算/两个预算的帧数**（该指标比 p99 更抗环境噪声，是本报告的主判据）。

### 4.1 首页，8 轮配对 + 顺序反转对照（最关键的一组）

`raw-home-ab.json`（顺序 A→B）：`raw-home-ab-rev.json`（顺序 B→A，**同样两臂**）

| run | 臂 | 逐轮 >7ms | 逐轮 p99 | 逐轮 p50 |
|---|---|---|---|---|
| ab | A-static | `4, 0, 0, 3, 0, 0, 0, 0` | `12.1, 6.3, 6.3, 12.2, 6.4, 6.3, 6.3, 6.3` | 全 6.1 |
| ab | B-shader1.0 | `1, 0, 3, 1, 99, 98, 0, 0` | `6.5, 6.3, 12.1, 6.6, 18.2, 24.2, 6.2, 6.2` | 全 6.1 |
| ab-rev | B-shader1.0 | `3, 0, 54, 9, 3, 0, 1, 0` | `12.3, 6.3, 18.3, 24.1, 12.1, 6.2, 6.3, 6.2` | 全 6.1 |
| ab-rev | A-static | `0, 0, 120, 0, 0, 0, 0, 0` | `6.3, 6.3, 29.8, 6.2, 6.2, 6.3, 6.2, 6.2` | 一轮 12.1 |

同轮配对 Δ（臂 − 静态）：ab 里 B 的 Δ>7ms 中位 **+0.0**、均值 +24.4、**8 轮里 3 轮更差**；
ab-rev 里中位 **+0.5**、均值 **−6.2**、8 轮里 4 轮更差。
**把两臂换个位置，谁更差就换了** —— 这是「噪声主导」的定义性证据。

### 4.2 首页，全部 run 加总（说明离散度有多大）

| 臂（同配置可能出现多个标签） | 轮 | 帧 | >7ms | >12ms | p99 中位/最大 |
|---|---|---|---|---|---|
| A-static（含多 run） | 36 | 10142 | 260 (2.6%) | 216 (2.1%) | 6.30 / 29.8 |
| A2-static-dup（**A 的副本**） | 5 | 1495 | 58 (3.9%) | 47 (3.1%) | 12.10 / 18.2 |
| B-shader1.0（标签合计） | 28 | 7477 | 1104 (14.8%) | 985 (13.2%) | 12.15 / 36.4 |
| **B-1x-oct3（与上面同一配置、换个 run）** | 4 | 1196 | **4 (0.3%)** | 2 (0.2%) | 6.25 / 6.3 |
| **B1-shader1x（同一配置，再一个 run）** | 3 | 897 | **1 (0.1%)** | 1 (0.1%) | 6.20 / 6.2 |
| B2-shader1.0-dup（**同一配置的副本**） | 5 | 1124 | 361 (32.1%) | 321 (28.6%) | 18.40 / 24.4 |
| D-shader0.5 | 5 | 1495 | 27 (1.8%) | 22 (1.5%) | 6.20 / 12.2 |
| F-1x-oct1 / S-1x-once / T-1x-fps30 / G-half-oct3 | 各 4 | 各 ~1100 | 0 / 0 / 3 / 2 | 0 / 0 / 3 / 2 | 6.20 |

**同一个配置（1x、3 层、每 rAF 重绘）在不同 run 里落在 0.1% 和 32% 之间**，而**同一 run 里两条
完全相同的臂也可以一个 0.3%、一个 32%**（ctl run 的 `B` 与 `B2-dup`……反向地，mech run 里
`B-1x-oct3` = 0.3% 而同 run 的 `A-static` = 12.5%）。这不是「哪个臂更差」，这是环境在动。

**环境确实在动**（`sampler.py` / `cpu-main.log`）：本机持续跑着 **18–58 个 msedge 进程、
18–24 个 python 进程**；跑测期间整机 CPU **24–67%，峰值 83%**。多轮坏掉的时段与 CPU 抬升吻合。
结论按纪律写：**首页上 shader 臂与静态臂的差异小于轮间波动，只写机制、不写数字**。

### 4.3 重页（`/courses/regression-analysis/chapter-01/notes/`，6 轮配对）

| 臂 | 逐轮 >7ms | 逐轮 p99 | p50 | 加总 >7ms / >12ms |
|---|---|---|---|---|
| A-static | `55, 33, 56, 5, 19, 25` | `18.2, 12.2, 18.2, 12.1, 12.2, 12.2` | 6.1 | 383 (11.7%) / 344 (10.5%) |
| B-shader1.0 | `37, 70, 15, 22, 15, 18` | `12.2, 18.2, 12.2, 12.2, 12.2, 12.2` | 6.1 | 348 (10.6%) / 295 (9.0%) |

同轮 Δ>7ms：中位 **−5.5**（shader 略少），6 轮里 2 轮更差。另有一组 5 轮的（`raw-notes.json`，
含 0.5x 与 2 层噪声）同样没有任何一臂跑出差异：p99 中位全是 12.20。
**这一页的瓶颈是页面自己**：静态臂每 299 帧就有 28–30 帧掉到 12.2 ms（≈10%），所有臂都一样；
再加 0.13 ms 的背景根本没有可分辨的位置。

### 4.4 过载标定（把像素数推上去，看仪器在什么量级才报警）

| 臂 | px/帧 | 逐轮 >7ms | 逐轮 p90/p99/max |
|---|---|---|---|
| A-static | – | `0, 0, 0` | `6.1/6.2/6.3` ×3 |
| B1-shader1x | 3.13 Mpx | `1, 0, 0` | `6.1/6.2/12.1` |
| B2-shader2x | 12.53 Mpx | `0, 0, 21` | `…/30.3/42.5` |
| B4-shader4x | 50.13 Mpx | `0, 65, 23` | 一轮 `48.6/97.3/115.1` |

4x 这组值得单独说：它的帧间隔崩了（max 115 ms、帧数掉到 124/2.2 s），但**同一次测量里它的
shader pass 只有 1.37 ms**。也就是说**崩的不是着色，是那张 9352×5360（约 200 MB）的 canvas 层**——
合成/显存的账。**第一个该拧的旋钮是像素数，不是噪声层数。**

### 4.5 3D 卡臂（`window.homeDeck.openAt(0)` + 每帧拖着不放）

`raw-home5.json` 同一 run：

| 臂 | 逐轮 >7ms | 逐轮帧数 | 卡的调速器 |
|---|---|---|---|
| C0-card+static（无 shader 对照） | `0, 101, 3, 121, 100` | `299, 258, 299, 240, 258` | r2/r4/r5 降到 tier 2，p75 12.1 ms |
| C1-card+shader | `0, 136, 111, 131, 96` | `299, 157, 222, 191, 236` | r2–r5 都降到 tier 2 |

- **有可用的对照**：`__bg.stats()` 证明 shader 真在出帧（每轮 bg 帧数 ≥ 录制帧数）；卡也在真跑
  （`drag` 计数 241–367，`card3d.stats().frames` 同轮增长）。
- **不可归因**：**没有 shader 的 C0 也把画质从 tier 0 降到了 tier 2**（`q.p75=12.1ms`，卡的判据是
  「p75 > refresh×1.25 = 7.5 ms 就降档」）→ 降档是当时整机状态造成的，不是背景抢了卡。
- **这一臂与 A/B 不可直接比**：弹层会把页面滚动限制住，C0/C1 每轮只录到 240–290 帧（A/B 是 299），
  页面负载被改变了。所以 C 只用于「两个 WebGL 上下文共存」的定性判断，不参与定量排名。
- 结构性事实（读代码 + 实测）：卡的 rAF **静止就停**，背景的 rAF 一直跑；两者各自
  `requestAnimationFrame`，**没有任何协调**。WebGL 上下文是按渲染进程限量的资源，背景会常驻占一个。

### 4.6 降级代理：`--disable-gpu`（SwiftShader 软件光栅）

同 2.218 s 录制窗口，帧数直接可比：

| 臂 | 逐轮帧数（6 轮） | 平均 fps | p50 | 相对静态 |
|---|---|---|---|---|
| A-static | `27, 30, 29, 22, 29, 27` | 12.3 | 78.8–85.0 ms | – |
| B-shader1.0 | `21, 21, 21, 24, 21, 19` | 9.5 | 85.0–103.0 ms | **−22%** |
| D-shader0.5 | `22, 23, 23, 24, 28, 23` | 10.7 | 72.7–96.9 ms | **−12%** |

**但这个代理不干净**：`--disable-gpu` 连合成器一起软件化了，所以**静态臂自己也只剩 12–13 fps**
（p50 79 ms）。它证明的是「页面本来就撑不住时，背景再砍掉约 1/5 的帧率；画布减半能把这一刀减到一半」，
**不能当成弱核显的绝对数字**（弱核显的合成仍然是 GPU 加速的）。

## 5. 还剩多少帧预算

- 实测帧周期 **6.1 ms**；安静状态下**所有臂**的 p99 都是 6.2 ms、p50 都是 6.1 ms、>7ms 的帧 0–1/300。
  也就是说页面本身几乎吃满了每一个 vsync，仪器在这个量级上的**分辨率就是一帧**（下一档是 12.1 ms）。
- 由 1x 臂从未越线 + 实测 shader 0.129 ms ⇒ 页面自身的每帧工作量 ≤ 5.97 ms。
- 由 §3 的预测性验证可知：一旦某帧总量越过 6.1 ms，帧率**立刻**掉到下一档（8.09 ms 的 shader →
  85 fps，间隔≈2×vsync）。**所以余量不厚**：这 0.13 ms 装得下，但「装得下多少别的」没有余量可分。
- 换句话说：**shader 背景不是压垮帧预算的东西（2.1%），但它花掉的是本来就所剩无几的余量里的
  2.1%；真正的风险在别处 —— 页面自身的负载波动（重页已丢 10%）和本机这种级别的后台争抢。**

---

## 6. 结论：能不能上

**能上**，依据是直接测量而不是外推：
1. 出货配置（3.13 Mpx、3 层噪声、每 rAF 重绘）→ **GPU 0.129 ms/帧、主线程 0.007 ms/帧**；
2. 真页面 A/B：安静轮里静态臂与 shader 臂都停在 p50 6.1 / p99 6.2，**差异小于环境波动**
   （换臂顺序，谁更差就反过来）；重页上两者都掉 10% 左右，与背景无关；
3. 卡臂上，**没有背景的对照臂自己也把 3D 卡画质降了档** → 不是背景抢的。

**但要带上 §7 的策略**，因为：余量本来就薄（页面自身 ≥5.97 ms/6.1 ms）、重页已经在丢 10% 的帧、
本机的后台争抢能把任何一臂按到 12–24 ms。

**首要风险不在帧预算，在文字对比度**：`--bg-mask-light/dark-1..3` 的三档 alpha 是按**一张静态图的
亮度**调出来的（仓库里的 `.shots/girlbg/contrast.js` 甚至把中档硬编码在 t=0.52），换成会变的背景后，
正文底色的亮度会**逐帧变化**，那张 12 组对比度表会在不报错的情况下失效。这条**本实验没有测**
（见 §8）。

## 7. 降级与暂停策略建议（每条标注证据强度）

| 策略 | 建议 | 证据 |
|---|---|---|
| `prefers-reduced-motion: reduce` | **整支脚本不挂载**（不是「画一帧静止图」） | **实测**（`rm_check.py`）：`mq=true`、`canvas=false`、`__bg.why='reduced-motion'`，且静态壁纸**保留**（bgimg 末尾仍是 webp URL） |
| 回退顺序 | **只在 GL 上下文 + 着色器都成功之后**才 `--bg-image-*: none` | **实测踩过**：第一版把摘图写在注入开头，reduced-motion 下变成「没有背景」。改后复测：reduce 时保留原图、正常时替换成功（`noStatic=true`） |
| 页面不可见就停 rAF | 已有（`visibilitychange` → `stop()`），切回来重启 | **实测**：早期一次 run 里页面被盖住时 `running=false` 且 `lastStop` 被写 → 停机路径真的走到过；省下 0.129 ms/帧 |
| 重绘上限（`fps`） | **做成 30 fps**：每帧唤醒但每 33 ms 才画一次 | **实测**：同一 2.2 s 窗口里 draw 次数从 **367 降到 61（6×）**，而帧间隔在任何安静轮里都量不出差别（T-1x-fps30 = 0/3 帧越线）。缓慢流动的极光看不出来，省了 83% 的 GPU 提交 |
| 画布像素上限 | **第一步就限制 canvas 像素**（dpr 封顶 1、或按设备档位给 0.5–0.75× 再 CSS 拉伸） | **实测**：代价随像素近似线性（0.077/0.129/0.519/1.368 ms）；4x（50 Mpx）时帧间隔崩到 max 115 ms **而 shader 本身只有 1.37 ms** → 崩的是 canvas 层，所以旋钮是像素数 |
| 「静态 shader 背景」档 | 兜底档可以是**只画一帧**的 shader（不跑 rAF） | **实测**：S-1x-once 4 轮 0 越线，与 A-static 同级；而它可以完全避免每帧提交 |
| 低端设备 / 无 GPU | 回退静态图（并保留原 webp 的 96.8 KB 预算） | **半测**：SwiftShader 下静态页已 12–13 fps，加背景再 −22%（0.5x 时 −12%）。**弱核显的真实代价未知**（§8） |
| 与 3D 卡共用 GPU | 弹层打开期间**把背景 rAF 停掉**（或降到 5 fps） | **机制确定**：卡静止就停、背景一直跑，两者无协调；卡的调速器判据是它自己的 p75 > 7.5 ms 就降档，而它在**没有背景**时也降过档 → 弹层期间把预算全留给卡是零风险的选择。定量收益**未测**（C0/C1 被判为不可比，见 §4.5） |

## 8. 没测到 / 未知（写清楚，不编）

1. **弱核显（Intel/AMD iGPU）的代价：未知**。`--disable-gpu` 不干净（合成器也软件化了），
   只能给出「页面撑不住时背景再砍 ~1/5 帧率」这一相对量。要绝对数字得在有 iGPU 的机器上复测。
2. **文字对比度**：未测。静态壁纸换成会变的背景后，蒙版模型失效的风险是本次最需要补的一条
   （建议：把 shader 的亮度范围钳制到被替换图片的范围，或重调 `--bg-mask-*` 并让 `.shots/girlbg/`
   的对比度脚本按多帧取样）。
3. **臂间差异的定量归因：不可归因（噪声主导）**。首页上同一配置跨 run 落在 0.1%–32%；
   换臂顺序会翻转结论；同 run 内两条相同臂也能差 100 倍。只有两处差异是明确的：过载（2x/4x）
   与软件光栅。
4. **C 臂与 A/B 不可比**：卡弹层限制页面滚动，录制帧数 240–290 vs 299。
5. **SW/主题切换场景**：`bg-switch.js` 的交叉淡入（ghost 层）+ shader 同时存在未测；浅/深主题切换
   （shader 是深色极光）只看了浅色主题 mask 下的表现 —— 浅色主题的蒙版 alpha 只有 0.1–0.14，
   实测深色 shader 会明显透出来（截图可见），这正是 §6 的对比度风险。
6. **只测了 2 个页面**（首页 + 一个重页）；卡只在首页测（重页没有卡）；滚动是合成的极端负载
   （重页 41250 px/s），不是真人脚本。
7. **帧间隔仪器的分辨率 = 1 帧**（6.1 ms）：比它小的代价只能靠 GPU 计时器，不能靠帧间隔。
8. 每轮未记墙钟时间戳，所以「哪一轮撞上了哪个后台突发」只有 CPU 采样日志的粗粒度对应。
